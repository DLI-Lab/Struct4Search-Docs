# 기준 성능과 회귀 판정

변경 전후를 비교할 기준선을 정하고, 병합해도 되는지 판정합니다.

## 기준선은 값 하나가 아닙니다

측정값만 적어 두면 재현할 수 없습니다. 기준선을 남길 때 다음을 함께 기록합니다.

| 항목 | 이유 |
|---|---|
| 코드 commit | 단계 구현이 결과를 바꿉니다 |
| 실행 프로파일 | 임계값·모델·자원이 여기 있습니다 |
| 인덱스 이름과 생성 시각 | 어느 색인을 쟀는지 |
| 평가셋 릴리스 | 자산이 바뀌면 값이 바뀝니다 |
| 문서 전처리 모델과 답변 모델 | 두 축을 구분해야 합니다 |
| 측정 날짜 | — |

앞의 다섯 가지 중 하나라도 다르면 **다른 조건의 값**입니다. 나란히 놓고 좋아졌다 나빠졌다 말할 수 없습니다.

## 회귀 판정 기준

- 테스트가 모두 통과해야 합니다.
- 검색 지표가 기준선 아래로 내려가면 병합하지 않습니다.
- QA 정확도가 기준선 아래로 내려가면 병합하지 않습니다.
- 인용 정리 집계가 0이 아니면 실패로 봅니다.
- 평가 결과에는 commit·프로파일·모델·인덱스·평가셋 릴리스를 함께 저장합니다.

네 번째 줄이 중요합니다. 인용 집계가 0이 아니라는 것은 모델이 계약을 어겼고 후처리가 그것을 지웠다는 뜻입니다. 지워졌으니 답변은 멀쩡해 보이지만 **원인은 남아 있습니다.**

## 무엇을 바꿨을 때 무엇을 다시 재는가

| 바꾼 것 | 검색 평가 | QA 평가 |
|---|---|---|
| 파싱·청킹·NER·KG 구축 | 필수 | 필수 |
| Metadata·검색표현 프롬프트 | 필수 | 필수 |
| 검색 파라미터·점수 통합 | 필수 | 필수 |
| Context 구성 | — | 필수 |
| 답변 프롬프트·모델 | — | 필수 |
| 동시성·서비스 주소 | — | — |

검색만 재고 넘어가지 않습니다. 검색 지표가 올라도 Context가 바뀌면 답변이 나빠질 수 있습니다.

## 구성을 둘 이상 운영할 때

문서 전처리 모델을 두 가지로 운영한다면 **각각의 기준선을 따로 유지합니다.** 하나만 기준선으로 두고 다른 구성을 그 값과 비교하면 모델 차이가 회귀로 잘못 읽힙니다.

## 기준선을 다시 잡아야 하는 때

| 상황 | 이유 |
|---|---|
| 평가셋 릴리스가 바뀜 | 이전 기준선은 이전 자산의 값 |
| 인덱스를 새로 만듦 | 색인 내용이 달라짐 |
| 문서 전처리 모델을 바꿈 | 검색 대상 자체가 달라짐 |

이 경우 이전 기준선과의 비교는 의미가 없습니다. 새 조건에서 다시 측정해 새 기준선으로 삼습니다.
